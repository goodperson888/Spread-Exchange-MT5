# 执行提速与高频点差对冲借鉴

依据：用户提供的两张产品成交表，以及本程序 G4 组执行诊断。截图未展示完整开平仓回执，以下区分观察结果与待验证假设。

## 本次已落实

- 已核验的不同 MT5 终端默认并发开仓，提供串行选项；同一终端双品种、交易所 × MT5 保留串行。
- 交易组与两腿意图一次事务保存，两个线程就绪后共同放行；快速回报立即由引擎主线程保存，不等另一腿返回。
- 未知回报按原 ID 查询，不重复开仓；拒单和部分成交按确认数量保护性减仓。重启不重放开仓。
- 两腿已经确认全额成交时，不仅因为请求返回慢而撤掉完整对冲；未知回报超过确认窗口仍走原保护流程。价差滑移保护继续独立生效。
- MT5 配对轮询间隔可配置，默认 50 毫秒；行情推送仍可立即唤醒。不会把重复旧报价伪造成新报价。
- 发送时记录本腿报价年龄、双边报价收到时间差、并发派发间隔，复用现有日志写入，无额外平台请求。

并发减少第二腿等待，无法保证第一腿滑点消失。当前没有证据表明 Python 计算是主要瓶颈；先比较真实并发前后的报价年龄、派发间隔、调用耗时与价差保留情况，再决定是否值得更换语言。

## 截图可以观察到的规律

- 产品关联主订单号与对冲订单号，存在不同买卖方向、小手数以及很多交易行。
- 第二张图中，0.05 手、开仓点差 6 对应获利 0.20；开仓点差 8 对应获利 0.30。若每手 100 盎司且获利是双边合计，则分别捕捉每盎司 0.04、0.06 美元。
- 部分相同设置下的行按手数折算收益，与开仓点差呈线性关系；这支持继续检查共同退出价差或同一时刻估值，不能据此确定固定退出阈值。
- 表格缺少明确平仓时间、两腿成交价格、手续费、Swap、返佣到账和 Point 定义，不能判断是否全部已平、真实净利润、持有时间或复原准确策略。

## 值得借鉴、但需单独验证的方向

1. **按终端对维护成交质量。** 比较每腿报价年龄、派发间隔、请求耗时的中位数和慢单分位数，并同时看实际价差恶化、拒单及部分成交比例。最终优选成交后仍保留优势的终端对。
2. **统计每手最终净收益。** 把两腿开平仓成本、已核验佣金、隔夜费与预计返佣分列，避免用订单数、胜率或预计返佣代替已结算收益。
3. **检查短暂报价不同步。** 用本机收到时间、平台原始报价与后续真实成交判断机会是否可执行。旧行情造成的尖峰不能直接作为套利优势。
4. **围绕相对偏离研究入场。** 对有稳定价差基准的终端对，验证偏离后能否回归；短窗口和长窗口都需要保留独立时间段验证，不能只优化截图那一段。
5. **频率由净优势决定。** 先验证往返后留存的价差足以覆盖费用和滑点，再研究缩短冷却或提高次数。此次不自动改变用户的入场、退出、手数与冷却参数。

以上是可验证的设计方向，不代表截图产品已采用这些机制。

## 带宽 0.7 的含义

下沿 = A Bid − B Ask；上沿 = A Ask − B Bid。

带宽 = 上沿 − 下沿 = A 自身买卖点差 + B 自身买卖点差。

带宽为 0.7 代表买卖点差摩擦，不是每次能赚 0.7。若开平仓时带宽均为 0.7，且两平台中间价差不变，往返毛收益约为每合约数量 -0.7，尚未计算其他费用。研究重点是整条带的位置变化与实际可执行开平仓价差。

## 验证边界

本机用模拟适配器验证并发、事务失败、线程创建失败、部分成交、未知回报与重启；并发不等于平台原子成交。Windows 经纪商环境的真实耗时和收益改善需后续执行诊断确认。

本次单次模拟对比：固定两腿适配器等待 120／80 毫秒，串行整组 209.215 毫秒、派发间隔 123.407 毫秒；并发整组 124.595 毫秒、派发间隔 0.010 毫秒。仅用于确认串行等待已移除，不能作为实盘耗时或收益承诺。
